# 3D reference replacement: Clip Studio Paint parity review

Review date: **7 November 2026**. Status: **implementation in progress; full parity not complete**. The artist rejected the existing skeleton-building/weight-painting workflow and requested a Clip Studio Paint style drawing-reference system. The [implemented reference workspace](3d-reference-workspace.md) now includes the asset/import/posing/material foundation and native drawing-canvas reference layers. Full workflow parity remains the acceptance target. Stages below sequence the work; they do not reduce that target.

The artist reviewed the model/posing workspace and explicitly approved adding it to the normal application on **7 November 2026**. The compatibility-named `TOON_ENABLE_EXPERIMENTAL_3D` option now defaults to ON, exposing **View → 3D reference…**; explicit OFF remains supported. Legacy rig/weight authoring stays retired in both configurations. This approval covers the implemented workflow and does not certify full CSP parity. Existing saved legacy scene data and compatibility rendering are retained.

The native layer follow-up places the reviewed models directly on the drawing canvas through docked Library/Controls. Translate/rotate/scale, joint FK, scene-camera gestures and the existing precise pose/shape/expression controls edit the drawing’s authoritative scene. **Draw above** creates a paintable raster layer. Project format 41 introduced portable reference-layer source and deduplicated canonical assets, including managed drawing revisions. This closes the basic canvas placement/draw-over gap; it does not certify every manipulation, capture, rendering, interchange or full-parity requirement below. Static reference posing does not implement 3D pose animation.

## 1. What the replacement is

The artist places a figure, character, head, hand, prop or scene on the drawing canvas; selects it; manipulates it directly; changes supported proportions/expressions; poses it manually or from a reference image; and saves reusable materials. The normal workflow starts with a usable model, not an empty skeleton. No skeleton creation, bone parenting, skin binding or weight painting is required to use supplied figures or compatible imported characters.

Underlying rigging remains necessary for articulation, but it is asset infrastructure. Imported characters arrive rigged; compatible skeletons are mapped to semantic body parts. Any preparation for unsupported rigs belongs in a focused import/setup path rather than the everyday pose controls. No generic automatic-rigging promise is part of this plan.

### Benchmark and evidence boundary

The checked Windows/macOS release is **Clip Studio Paint 5.1.5**, released 5 October 2026. The online manual and the 5.0/5.1 additions are the reference, rather than a reduced older feature list. Studio Mode desktop behavior is the primary comparison because Toon Pro is a native desktop application. Mobile camera/file-picker differences are documented separately. [Current release notes](https://www.clipstudio.net/en/dl/release_note/latest/).

This is an engineering review of official documentation, not a completed hands-on comparison in a locally installed CSP session. Artist acceptance must compare the actual applications and representative assets. Original implementation and appropriately licensed assets are required; this plan does not assume access to CSP's implementation or bundled meshes.

### Boundaries that matter to “exactly the same”

1. **Adjustable figures, adjustable heads and imported characters are different asset classes.** Arbitrary OBJ geometry does not contain bones, semantic facial regions or morph targets. A rigged GLB may contain all of these, some, or none. Built-in figures/heads/hands must be authored for their advertised parameters. Uploaded characters expose what they actually support, with an explicit preparation path for missing mappings. This follows the separation in CSP's [material overview](https://help.clip-studio.com/en-us/manual_en/660_3d/3D_Tools.htm), [head controls](https://help.clip-studio.com/en-us/manual_en/660_3d/3D_Head_Models.htm) and [character controls](https://help.clip-studio.com/en-us/manual_en/660_3d/Editing_a_3D_Character_Material.htm).
2. **Body shape and facial expression are separate deformation systems.** Height/chin proportions need authored shape data; a smile/blink needs expression targets or facial bones. Adding a slider cannot supply the missing geometry. The same limitation applies to Toon Pro, even if an imported model is poseable.
3. **Image posing is estimation followed by correction.** A single image does not determine hidden joints or unique 3D depth. Body and articulated-hand detection require different models; camera matching and retargeting remain engineering work. Preserve the reference image and correction workflow. See the [Pose Landmarker](https://developers.google.com/edge/mediapipe/solutions/vision/pose_landmarker) and [Hand Landmarker](https://developers.google.com/edge/mediapipe/solutions/vision/hand_landmarker) task descriptions.
4. **CSP materials are not automatically portable files.** `.cs3c`, `.cs3o`, historical `.c2*`, `.clip`/3D image materials and the Assets service are not glTF aliases. Do not promise importing the artist's entire CSP library until actual file types, available exports, license metadata and representative samples are tested. A standard-format asset pipeline is implementable without claiming proprietary-format support. [CSP import formats](https://help.clip-studio.com/en-us/manual_en/660_3d/Importing_3D_Files.htm).
5. **The manual contains a stale VRM limitation.** The import page says morph expressions are unsupported, but the dedicated character page documents expression controls and release notes added them in 3.2. Use the newer capability as the target. [Character materials](https://help.clip-studio.com/en-us/manual_en/660_3d/Editing_a_3D_Character_Material.htm), [3.x release notes](https://www.clipstudio.net/en/dl/release_note/v3/).

These are asset and evidence constraints, not reductions of the feature target. Record unmet requirements as open; the approved partial workflow must not be renamed “CSP parity.”

## 4. Proposed implementation architecture

The names below describe proposed modules, not existing files or shipped APIs.

### Asset and scene domain

- `ReferenceAsset`: immutable meshes, original node hierarchy, local TRS/quaternions, units/axes, materials/textures, skins, inverse-bind matrices, joint influences, sparse/dense morph targets, bounds and source/license metadata. Preserve authored object shape keys, layouts, material/body/hair/accessory variants, movable-part definitions and secondary-motion metadata.
- `HumanoidDefinition`: semantic mapping for hips/spine/chest/neck/head, limbs, feet/toes and finger chains; rest pose, local axes, joint ranges, mirror pairs and attachment sockets. Preserve extra bones instead of flattening a character into a hard-coded template.
- `ShapeDefinition`: authored parameter names/ranges, model compatibility, morph combinations, bone-length/width rules, pivot corrections and corrective targets. Shape evaluation precedes posing; update IK lengths, bounds and collision/contact proxies after shape changes.
- `ExpressionDefinition`: authored morph/bone/material bindings, permitted combinations, overrides for blink/look-at/mouth and named expression presets. VRM mappings are an adapter to this domain.
- `ReferenceInstance`: asset ID plus placement, shape, pose, expression, material overrides, attachments and visibility/lock state. Instances share immutable asset buffers while retaining independent edits.
- `ReferenceScene`: one document reference layer's ordered object hierarchy, camera/views, lighting, ground/shadows, panorama, fog and drawing-guide relationship. Support multiple independently composited reference layers with separate cameras, opacity and visibility. Model/world/camera/artwork coordinates must have one documented conversion contract.
- `MaterialRecord`: typed reusable preset, stable ID/version, compatibility requirements, dependent asset hashes, thumbnail, tags, attribution and portability manifest. Pose records target semantic joints rather than internal IDs from one model.

For canonical import, use the [glTF 2.0 skin/morph/node specification](https://registry.khronos.org/glTF/specs/2.0/glTF-2.0.html). Support VRM0/1 with explicit adapters for humanoid mappings, expressions, gaze, materials, node constraints and spring bones; [VRM 1.0](https://vrm.dev/en/vrm1/) and [MToon](https://github.com/vrm-c/vrm-specification/tree/master/specification/VRMC_materials_mtoon-1.0) require more than merely parsing GLB geometry. Specify constraint evaluation and a rest/frozen/current-simulation-state policy for static references. Assimp is a candidate for additional formats, with [documented format coverage](https://github.com/assimp/assimp/blob/master/doc/Fileformats.md) assessed against fixtures. An imported extension or deformation feature must be preserved, explicitly converted with reviewed results, or rejected before publication.

### Evaluation, rendering and interactions

Evaluation contract: derive shape-adjusted geometry, skeleton and compatible bind/inverse-bind transforms from the immutable rest asset; evaluate pose/expression bindings and node constraints; apply morph deltas **before skinning**; evaluate attachments/world placement; then render through the camera/light state. Update IK lengths, collision/contact proxies and corrective bindings together when shape changes. Define expression-bone/constraint ordering to avoid double application. Spring evaluation must have deterministic reset/freeze behavior.

Manga Perspective needs its own camera-relative depth-deformation spike and collision-correction control: CSP preserves pose angle while exaggerating depth, so changing camera FOV alone cannot meet this requirement. Keep the deformation shared by display, picking and downstream line extraction. [Manga Perspective settings](https://help.clip-studio.com/en-us/manual_en/810_subtools/M.htm).

Retain Filament as the initial rendering candidate. The pinned 1.78.0 [RenderableManager API](https://github.com/google/filament/blob/v1.78.0/filament/include/filament/RenderableManager.h) supports skinning and morph weights; [gltfio's Animator](https://github.com/google/filament/blob/v1.78.0/libs/gltfio/include/gltfio/Animator.h) exposes bone-matrix updates independently of playing an animation. Confirm the linked SDK libraries, asset-loader route and joint/morph limits in a spike. Use GPU deformation for interactive posing where supported; provide a shared evaluated snapshot for CPU-dependent selection, bounds and line extraction. Do not build separate inconsistent deformation implementations for the canvas and line renderer.

Add ID-buffer or equivalent accurate object/part picking, ray/plane constraints and camera-independent handle sizing. Keep hit regions comfortable for a pen and readable at Retina scale. Prevent navigation from unexpectedly changing a pose. All commands operate through the document transaction boundary; async completion checks document/asset generation before updating previews or applying edits.

The public interaction model is **Select / Pose / Shape / Face / Hands / Scene / Camera / Light**, shown as meaningful tabs for the selected material's capabilities. Frequent actions remain near the model. Body maps, face-region diagrams, hand curl/spread controls, camera navigation and light-direction widgets provide real manipulation; scalar values retain the repository's slider/exact-entry pairing. Avoid a wall of unrelated bone fields or UI that implies unsupported shape capabilities.

### Asset production is a parallel workstream

Engine code cannot produce a high-quality figure library by itself. Commission/create original compatible base figures, heads and hands with clean topology, UVs, skin weights, named shape targets, expression data and deformation corrections. Establish parameter ranges and visual examples before wiring the controls. Include varied proportions and stylization, neutral rest poses, seam/hair/accessory cases, asymmetric expressions and extreme but valid poses.

Each asset needs provenance, source authoring files, target names/meaning, dimensions, rig mapping and expected output captures. Do not bundle third-party samples merely because an engine SDK includes them. Library quantity and the artist's preferred character styles remain review inputs; do not invent a completed catalog or reuse CSP meshes.

### Image and hand posing

Candidate pipeline: decode a bounded local image → user-selected subject/crop → body/hand landmark inference → confidence-marked 2D/3D preview → coordinate/camera hypothesis → semantic retarget → constrained IK/contact refinement → editable pose preview → one committed document command. Run inference off the UI thread, support cancel and reject stale results.

MediaPipe's [Pose Landmarker](https://developers.google.com/edge/mediapipe/solutions/vision/pose_landmarker) provides body landmarks; its [Hand Landmarker](https://developers.google.com/edge/mediapipe/solutions/vision/hand_landmarker) provides articulated hand landmarks. Choose a pinned native inference runtime/model only after a C++ packaging and quality spike on macOS and Windows; retain its precise version, model license and redistribution notices. Python/Web demos are evidence of a model capability, not proof of a deployable Qt feature. Evaluate occlusion, foreshortening, seated/lying poses, clothing, cropped limbs, image mirroring and stylized drawings. Preserve original proportions and let the artist correct ambiguous joints/depth. Report low confidence without replacing a valid existing pose.

## 5. Isolation, persistence and approval

`TOON_ENABLE_EXPERIMENTAL_3D` now defaults to **ON** following the artist's explicit approval of the reviewed workflow. Explicit OFF builds remain available. The first quarantine removed legacy 3D authoring from normal builds; the implementation keeps it retired in all configurations and uses the compatibility-named flag solely for the replacement workspace and standalone review app. Legacy placement, tools, inspectors, library entry points, restored/custom tool activation and controller mutation stay blocked without deleting catalog entries or serialized scene assets. Already-authored scenes retain compatibility display/storage.

Retain the explicit build option for opting out of the replacement and keep legacy rig/weight UI retired. Unfinished capabilities must remain accurately described. A setting migration, restored workspace, startup argument or renderer availability must not bypass an explicit OFF build. Hardware renderer availability is separate from artist-approved feature availability.

New scene/material formats require strict validation, bounded resources and atomic publication. A newly authored reference scene must save/reopen without external file dependencies. Existing projects must retain their old interpretation. Unsupported future data should fail clearly rather than loading as an empty scene. Keep an explicit legacy read adapter until compatibility checks and the artist's retention decision permit removal.

The artist's approval authorizes normal-app enablement of the implemented model/import/posing/material workspace. Passing tests alone did not authorize that change. Complete CSP parity still requires the evidence below and further acceptance of unresolved requirements. This local enablement does not publish or replace existing release packages.

## 7. Acceptance and evidence checklist

- **Placement/materials:** place multiple asset kinds; drag a pose onto an existing character; save body-only, head-only, hand-only, full-character and multi-object scene presets; apply them in another project; move/remove the source import and reopen successfully.
- **Pose correctness:** shoulder/twist and hip/knee bends, planted feet, wrist/finger extremes, locked limbs, different proportions, pose mirroring and pole continuity; no mesh explosions, unintended root jumps or flipped knees; check every exposed bone/part control against rendered deformation.
- **Shape correctness:** height matches measured units; head ratio and limb dimensions alter the actual model; chin/jaw/eyes/nose/mouth/ears and hand parameters produce the expected region changes; expressions combine correctly; corrective shapes prevent unacceptable deformation at tested extremes.
- **Imported characters:** multiple skins, differing rest orientations, extra/twist bones, transformed parents, normalized weights, sparse morphs, alpha cutout/blend, texture color spaces, VRM0/1, MToon and expression bindings. Unsupported cases produce explicit diagnostics before the model is added.
- **Scene/camera/light:** attachment hierarchy, custom head replacement, object grouping and snapping, locked cameras, separate 2D/3D navigation, perspective guides, focal length/orthographic views, transparent composition, outlines, fog, panorama, directional/ambient light, and actual cast/contact shadows.
- **Image inference:** front/side/three-quarter, seated/lying, foreshortened, cropped/occluded, mirrored photos, more than one person and separate hands; user can select the subject and correct uncertainty. Inference never silently alters body shape or applies to the wrong active character.
- **Workflow/UX:** common actions are direct; spatial settings have meaningful visual interaction; exact scalar controls stay synchronized; tooltips use 600 ms; keyboard and physical pen interactions remain usable; no focus loss or extra Apply for ordinary drags; one gesture is one Undo.
- **Persistence/safety:** pose/shape/expression/material/hierarchy round-trips; cancel and undo/redo; missing/corrupt assets; bounded hostile imports; asynchronous stale completion; source-safe copies; new document versions and old scene compatibility. Flag-off catalogs retain hidden customization data.
- **Performance/platforms:** measure input-to-preview latency, drag-frame time, cold import, peak CPU/GPU memory and save size for documented single/multiple-character assets on macOS/Windows. Agree measured budgets before acceptance; current Apple-Silicon-only rendering is not desktop parity.
- **Review record:** per-requirement fixture, source, build/flag/backend, reproduction steps, actual capture, pass/fail and artist notes. Keep untested controls and unresolved visual differences open. No production promotion merely because a demonstration scene works.

## 8. Inputs for the first review build

The work can start with openly licensed engineering fixtures, so these inputs do not block quarantine or the domain spikes. Before certifying the artist's library and preferred character look, collect representative models with their actual file extensions, a few desired body/head/hand shapes, challenging reference photos, and the CSP desktop version/workflows the artist uses. Importing standard models and importing native CSP material packages are separate acceptance cases. Record unresolved cases without quietly narrowing “exactly the same.”
